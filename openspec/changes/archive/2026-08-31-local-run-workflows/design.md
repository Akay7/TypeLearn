## Context

The stack runs in a kind cluster, rendered from `chart/` by Tilt. Source is
synced into running pods, so ordinary editing needs nothing on the host at all.
Three things still do:

- **a debugger.** Tilt syncs files into a pod; it does not attach `debugpy` to
  one. Stepping through a view or a management command means running that
  process on the host.
- **the frontend, without the cluster.** The browser suite already does this —
  it stubs the catalog and runs against its own dev server — but a developer
  doing UI work against *real* exercises has no supported path.
- **backend tests, sometimes.** The Tilt button runs them in the pod, which is
  what CI does and is the answer that should stay. A single failing test is
  easier to understand under a debugger.

Two facts shape everything below.

**The single-origin property is not a deployment detail.** The Gateway serves the
SPA, the GraphQL endpoint and the audio from one address, which is the entire
reason `django-cors-headers` could be deleted. Any host workflow that puts the
frontend on one origin and the backend on another re-creates the problem, and the
backend has nothing left to answer a preflight with. Today's fallback address,
`http://localhost:8000/graphql/`, is exactly that arrangement, surviving as a
default nobody exercises.

**The database is deliberately unreachable.** No port is exposed and the password
is generated by CloudNativePG into a Secret, so it appears in no file in this
repository. That is correct, and it is why a host process needs help rather than
a `.env` entry.

## Goals / Non-Goals

**Goals:**

- Run the frontend on the host against the real backend, same-origin, with no
  extra setup beyond what `tilt up` already provides.
- Attach a debugger to the backend where it already runs, so what is stepped
  through is the artifact rather than a reconstruction of it.
- Keep backend tests in the pod, and say so.
- Whatever forwarding is required is performed by the tooling, not by the
  developer as a documented prerequisite.

**Non-Goals:**

- A second way to deploy the stack. Nothing here describes what runs where; a
  host process is a *client* of the cluster, using its database and its Gateway.
  The chart stays the only description of the stack.
- Running the whole application on the host. That is the two-origin arrangement
  the cluster removed, and re-creating it is the outcome this design exists to
  prevent.
- Changing anything about the cluster path, the chart, the images, or CI.
- Running the application on the host at all. That was the first shape of this
  design and it was wrong: see below.

## Decisions

### 1. The dev server proxies backend paths, so the browser still sees one origin

`vite.config.js` gains a `server.proxy` forwarding `/graphql/`, `/media/`,
`/admin/` and `/static/` — the same four prefixes the HTTPRoute sends to Django,
which is not a coincidence and should be kept in step deliberately. The page, its
assets and its data then all come from `http://localhost:5173`, so the browser
issues no cross-origin request, sends no preflight, and needs no CORS headers.

This is the same shape the Gateway provides, implemented by the dev server for
the case where the frontend is outside the cluster. It means the frontend's API
address can be a path rather than a URL in *every* environment, which is why the
fallback changes to `/graphql/`.

*Alternatives considered.* Adding CORS headers to the backend for development —
this is precisely the thing a whole change was spent deleting, and it would make
local development the only environment needing them, which the
`local-dev-environment` spec forbids in as many words. Pointing the frontend at
the Gateway with an absolute URL — same cross-origin problem, moved.

### 2. The proxy target defaults to the Gateway Tilt already forwards

`VITE_PROXY_TARGET` selects where proxied paths go, defaulting to the worktree's
Gateway port. Tilt forwards it already, so the common case — the frontend on the
host, everything else in the cluster — needs no new machinery, no second backend
and no database.

Setting it to `http://localhost:8000` instead points the same dev server at a
host backend, which is the debugger case. One variable, two workflows, and the
browser cannot tell the difference.

The default has to know the worktree's port, which `scripts/worktree-env.sh`
already derives and is the single source of that mapping. The config reads it
from the environment with the same 8500 fallback rather than shelling out, so
`vite.config.js` stays a config file.

### 3. The debugger attaches to the container, and nothing runs on the host

`backend.debug.enabled` makes the backend run under `debugpy`, and Tilt forwards
the attach port. An editor connects to it and sets breakpoints against source
that Tilt has already synced into the pod, so the mapping between the two is
one-to-one and is stated explicitly rather than inferred.

This is better than the alternative it replaces on every axis that matters. What
is debugged is the image a deployment runs, with its environment, its database
and the Gateway in front of it — there is no reassembled copy that can differ.
No database password leaves the cluster, no database port is opened, and there
is no script resolving credentials, because there is nothing on the host that
needs them.

Two details are deliberate. Nothing waits for a client: a pod that blocks until a
debugger attaches is a stack that looks broken to everyone not debugging. And
under the debugger the backend runs Django's own server single-process rather
than gunicorn, because gunicorn forks its workers and a breakpoint in request
handling would land in a child the debugger never sees. Same image, same
environment, same routing — only the server process differs, and only while
debugging.

*Alternatives considered, and one of them was built first.* Running the backend
on the host against a forwarded database: it needs the cluster's generated
password copied out, it opens the database to the host, and what it debugs is not
what runs. It was implemented before being abandoned, and the reason it had to be
is recorded below.

### 4. Tests run in the pod, and nowhere else is offered

`pytest` in the pod is what the Tilt button runs and what CI runs inside the
built image, so it is the answer that matches what will be judged. No host
arrangement is offered, because one that ran the suite against something less
than the real database would make a green result mean less.

Frontend suites are unaffected: `vitest` is pure logic, and the browser suite
stubs the catalog and starts its own dev server. Neither touches the cluster, and
neither should start.

### 5. `.vscode` attaches, and stops describing procedures in comments

Two configurations: attach to the backend container, and run the frontend's dev
server. Neither needs a credential, a task, or a generated file. The Testing view
stays configured for collection and navigation and says plainly that running the
suite belongs in the cluster — a comment describing a procedure is a procedure
that drifts from the one that works.

### 6. Bring-up refuses a cluster that is not this project's

Every kind cluster looks equally local to Tilt, so with another project's context
selected `tilt up` would deploy this stack into it and leave a namespace, a
database and a Gateway behind. It now fails and names both the selected cluster
and the expected one. This is the same class of quiet wrongness the
container-runtime guard already covers, and it was hit for real while building
this change.

## What Building It Changed

The first shape of this design put the backend on the host against a forwarded
database. It was built, and then abandoned, for reasons only running it produced.

- **`kubectl port-forward` cannot keep this database reachable.** Against this
  cluster it exits the moment a single forwarded connection closes — verified
  with a bare `kubectl port-forward` on a fresh port, no script and no supervisor
  involved: connect once, close cleanly, and the forward is gone with `error:
  lost connection to pod`. Supervising it does not help, because a client that
  gets `connection refused` does not retry. Tilt's own forwarder survives and
  re-establishes, which was enough for a `runserver` and not enough for a test
  run, which opens several connections back-to-back and lands in the window.
- **So the host was the wrong place.** A debugger attached to the container needs
  one long-lived connection rather than many short ones, which is exactly the
  pattern that works — and it removes the reason the database had to be exposed
  at all. The whole apparatus that had been built for the host approach went with
  it: the credential-resolving script, the opt-in database forward, and the
  caveat that a host backend is not the backend that ships.
- **Vite's dev server sends `Access-Control-Allow-Origin` of its own accord.**
  Every proxied response carried one. Nothing needs it — every request is
  same-origin by construction — and a dev server advertising cross-origin access
  to an API that has none is how a developer comes to depend on a permission that
  exists in development and nowhere else. `server.cors: false`.
- **The wrong cluster was selected, for real.** Partway through this work the
  active kubectl context belonged to another project entirely, where `tilt up`
  would have deployed this stack. Hence decision 6.

One decision was confirmed rather than changed: `changeOrigin: false` means the
backend sees the host the browser actually used, so `audioUrl` comes back as
`http://localhost:5199/media/...` and the clip loads from the same origin as the
page. With the default it would have named the proxy's target instead.

## Risks / Trade-offs

- **Two proxy definitions can drift** — the HTTPRoute's four prefixes and the dev
  server's → they are the same list for the same reason, and a path added to one
  and not the other breaks the host frontend silently, in a way only a developer
  running it that way would notice. Mitigation: name the coupling in both files.
- **The debugged process is not gunicorn** → under the debugger the backend runs
  Django's own server, because gunicorn's forked workers put breakpoints in a
  child the debugger cannot see. Everything else is identical, and the difference
  is stated where it is switched on. A bug that only appears under gunicorn's
  worker model will not reproduce this way.
- **A forwarded debug port is a port** → it is off by default, opt-in per
  checkout, and carries no data. It is tooling, like the Tilt UI, rather than one
  of the application's services; the rule that the Gateway is the only service
  exposed is unchanged.
- **The frontend on the host is not the frontend that ships** → it is the Vite
  dev server, not the built bundle behind nginx. That difference already existed
  and is what `frontend.mode` describes in the chart; running it on the host adds
  nothing new to it.

## Migration Plan

1. Add the proxy and change the fallback address; confirm the browser suite still
   passes, since it exercises the same default.
2. Run the frontend on the host against the cluster Gateway and confirm real
   exercises load with no CORS header in any response.
3. Add `debugpy` to the dev group and the `backend.debug` branch to the chart;
   confirm a debugger attaches to the running container and the stack still
   serves.
4. Point `.vscode` at the attach configuration.
5. Rewrite the README's local section.

Rollback is reverting the commit. Nothing outside the repository changes: no
cluster state, no data, no image.

## Open Questions

- **Whether debugging a single test in the pod is worth an entry point.** It was
  the one workflow the host approach would have offered and this one does not.
  Deliberately left out for now; a second Tilt button running pytest under
  `debugpy` would be the shape if it is wanted.
